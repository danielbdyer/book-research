# the scaffold check lists every source of an expired section and cannot name the one that moved

The `/scaffold refresh` of 2026-09-03 opened on a report of seven expired sections — ARC, ANCHORS, R1DRAFTS, R2ARC, R4THINK, R7HOUSE, EVIDENCE — and no baseline drift. The whole cause was one uncommitted line in `ops/chapter concordance.md`, the row recording where the Afterglow's part-seam differs between the drafts and the descriptive sources, and the concordance sits in the source list of exactly those seven markers. The check said none of this. For each expired section it printed the stored and current checksums and the full `re-read:` list — twenty-one files for the evidence ledger, fourteen for the constellation — and the session established that a single file had moved, and what had moved in it, only by adding a git worktree at HEAD, running the check there (sixteen fresh), and diffing the working tree against it.

## The mechanism

A marker stores one CRC over the sorted `path:crc32` lines of its sources, so the check can tell that the bundle moved and cannot tell which member moved: the per-file checksums are computed on the way to the bundle value and thrown away. The `missing:` line is the one case where the check does name a file, because absence is visible without a stored per-file value. The appendix of `ops/scaffold.md` had described the check as naming "the source whose bytes moved," which the tool does only for a deletion; that sentence was corrected in the same refresh.

The cost scales with fan-out. `ops/chapter concordance.md` is watched by seven of sixteen scaffold markers and `ops/decisions.md` by three, the same shared-source cascade `ops/methodology/re-stamping a cache marker.md` records for the decisions register and the scaffold itself. Every one-row addition to the concordance therefore asks a session to re-read seven sections against a delta it has to find for itself.

## What would close it, and the evidence for each

- **Store per-file checksums in the marker and report the mover.** A `src=` grammar of `path@crc32|path@crc32` lets the check print `moved: ops/chapter concordance.md` beside `re-read:`. The real instance is today's: the diagnosis took a worktree checkout and would have taken one line. The cost is a change to the marker grammar, the parser, and `--crc`; every existing marker would be re-stamped once.
- **Have the check consult git.** For an expired section, `git diff --stat <commit at derived date> -- <sources>` plus the working-tree status names the movers without changing the marker grammar. Its limit is that it reports by commit time rather than content, which is the trade the content-hash design was made to avoid, and it says nothing when the mover is an uncommitted edit unless the check also reads `git status`.
- **Leave it to the session.** The worktree diagnosis is four commands and it worked. Its weakness is that it is undocumented and rediscovered each time, and that a refresh which skips it re-reads seven sections in full for a one-row delta.

The first option is the one that keeps the content-hash discipline intact; whether the grammar change is worth making is a `/rethink` question.

## A second instance, later the same day

The next `/scaffold refresh` of 2026-09-03 opened on one expired section, JOINTS, whose `re-read:` line listed six files. The mover was found in two commands and no worktree: `git log --since=<the stamp date> -- <the six sources>` showed one file with a commit after the marker's `derived=` date, and recomputing the marker's checksum at that commit's parent — the same sorted `path:crc32` formula, run over `git show <parent>:<path>` — reproduced the stored value `1d1e40ef` exactly, which proved that the auto-commit `acb0ba9` (one parenthetical in `notes/the solitary form stands against seven witnesses who hold a second person constitutive.md`) was the whole cause and that the other five sources had not moved. This bears on the second option above: the git route named the mover here, and the parent-commit recomputation closes part of the gap that route was said to leave, since it confirms by content rather than by commit time that nothing else in the bundle moved. Its remaining limit stands: an uncommitted edit is invisible to `git log` and needs `git status` read beside it. Two instances in one day, each diagnosed by a different undocumented route, are the evidence that the check should print the mover itself.

## A third instance, the same day

The third `/scaffold refresh` of 2026-09-03 opened on eight expired sections and no baseline drift, and every `re-read:` line again listed every source. The mover was found by one script and no worktree, by a route that also covers the case the second instance left open: for each expired section, recompute the marker's stored formula over `git show <rev>:<path>` at successive commits from `git rev-list` until the stored value reappears, then compare each source at that commit against the working tree. Every stored value reappeared at HEAD itself, which proved in one pass that the movers were uncommitted edits — two rows added to `ops/chapter concordance.md`, under seven of the eight sections, and three bullets plus a `treatment:` field in `notes/the solitary form stands against seven witnesses who hold a second person constitutive.md`, under the eighth — and that no other source in any bundle had moved. `git log --since` alone would have said nothing here, because nothing had been committed; the recomputation names an uncommitted mover as readily as a committed one, so the limit the second instance left standing is closed by this route without reading `git status`. Three instances in one day, diagnosed by three different undocumented routes, and the third is the one the check itself could run with what it already owns: its `--crc` formula, walked backward through the commit list until the stored value matches, then a per-file comparison. That is the second option above made true by content rather than by commit time. The script lived in the session scratchpad and was not persisted; if the check gains a `--moved` mode, this is its shape.

## A fourth instance, on the lens side, the same day

The second `/lens refresh` of 2026-09-03 opened on seven expired markers across six families and no baseline drift, and every `re-read:` line listed the whole bundle — ten files for `CON-register`, eight for `PAR-paired`. The movers were found by one script before any section was opened, by the third instance's route with one addition: for each expired marker it recomputed the stored formula over `git show <rev>:<path>` at each recent commit and, separately, substituted one source at a time from each commit into the committed HEAD state, so it named both the commit at which the stored value last held and the single file whose reversion restores it. The result sorted the seven markers into three causes. Five (`PAR-paired`, `CON-register`, `CON-bench`, `TB-joints`, `MAKE-frontier`) held at the parent of the auto-commit `acb0ba9` and were restored by one file alone, `notes/the solitary form stands against seven witnesses who hold a second person constitutive.md` — the committed parenthetical, plus three bullets and a `treatment:` field that `git status` showed still uncommitted. Two (`LOC-substrate`, `ARC-drafts`) held at committed HEAD itself, which proved their movers uncommitted: the eight entries added to `ops/reading queue.md` and the two rows added to `ops/chapter concordance.md`. And `TB-joints` carried a second uncommitted mover, `ops/scaffold.md`, visible only because the committed-blob comparison was read beside `git status`. The refresh therefore reread seven sections against four small deltas rather than against the forty-odd files the `re-read:` lines named. The script is `lens-movers.py` in the session scratchpad and not in `scripts/queries/`. Four instances in two days, three of them diagnosed by variants of the same recomputation, are the evidence a `/rethink` pass would weigh for a `--moved` mode.
